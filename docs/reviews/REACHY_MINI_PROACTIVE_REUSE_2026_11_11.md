# Reachy Mini and published proactive social robotics: source reuse for Desk Robot Remix

Research checkpoint: 2026-11-11. **This file is shared engineering knowledge, not a new software stack or evidence of hardware completion.** Keep [AGENTS.md](../../AGENTS.md), [parallel chat handoff](PARALLEL_CHAT_HANDOFF.md), and active draft [PR #17](https://github.com/hungngodev/desk-robot-remix/pull/17) authoritative. The user requires five complete tracked desk pets with individual identity, memory, natural voice interruption, multimodal vision, sensors, a grasping arm and genuine safe docking. Do not replace WROOM, XIAO Sense, Mac brain or final CAD with Reachy hardware; do not install an unrelated agent or a second media server merely to imitate a demo.

## November 12 camera and native audio orchestration: verified upstream contracts

The target is the existing **XIAO Sense JPEG camera and microphone**, not a second video server or a 30 FPS stream. The head firmware has a bounded one-frame PSRAM JPEG source and source boot/sequence/completion headers. `HttpHead.snapshot()` rejects stale/replayed sensor identity. The Mac `MultimodalOrchestrator` owns the camera lock, real VAD-prioritized samples, compressed-frame ring, motion scoring, visual request priority and VLM. Its `native_frame()` shares that same JPEG source with the optional Xiaozhi native duplex adapter; no second independent camera owner. Native audio remains one Xiaozhi microphone and Opus head speaker. Five pets share human turn priority and speaker cancellation; WROOM keeps local motor safety ownership.

Primary sources differ materially:

* [Google Gemini Live](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/send-audio-video-streams) accepts continuous 16kHz input PCM and **separate** JPEG video frames at up to 1 FPS, with 24kHz output PCM. This is a reference for behavior, **not** the currently configured model transport.
* [LiveKit VoiceActivityVideoSampler](https://docs.livekit.io/agents/multimodality/vision/video/) samples 1 FPS while a human speaks and about 0.3 FPS in silence. Speech VAD is an independent priority signal; idle video alone does not trigger model speech.
* [Reachy Mini conversation app](https://github.com/pollen-robotics/reachy_mini_conversation_app) uses one realtime conversation backend, camera tool, asynchronous tool calls and an expression/motion scheduler, not separate unlimited agents per sensor.
* **Critical compatibility constraint:** [vLLM Omni duplex client](https://docs.vllm.ai/projects/vllm-omni/en/latest/api/vllm_omni/clients/duplex/) says camera images ride the `input_audio_buffer.append` that **closes a complete one-second audio model unit**. Sending a frame earlier may strand it and misreport model vision. This differs from Gemini Live. A 200ms voice question may have no complete Omni video unit; the separate authenticated `desk_robot_look` tool with local VLM is the valid camera-question path for the original Xiaozhi conversational stack. Do not invent an early `video_frames` protocol guarantee or pad the human audio with unmeasured silence to fake a complete unit.
* [vLLM Omni tool-call capability table](https://docs.vllm.ai/projects/vllm-omni/en/latest/serving/realtime_duplex_api/) distinguishes models. A model-specific native tool callback cannot be assumed for MiniCPM-o: upstream tool-call support is not universally available. Original Xiaozhi registered tool calls already use authenticated Mac endpoints with a VAD generation fence, whereas the optional MiniCPM audio/video path must not be mislabeled as equivalent tool-capable Gemini Live.

This integration pass fixed the production bridge to carry the actual Mac `X-Desk-Camera-Receipt-Us` identity into `OmniDuplexWire.append_audio`, so one received JPEG is never replayed as a new video frame. Frame selection remains gated by a full one-second model unit, actual recent human speech, and strictly increasing camera receipt. Barge-in invalidates recent-speech eligibility so an old image cannot ride a new silent unit. The existing Mac `native_frame()` coalesces concurrent native audio/VAD captures under **one shared camera lock**. Corresponding regression source contracts check short-turn non-claims, valid 1 FPS unit boundaries, receipt deduplication, and barge-in.

**Evidence limitation:** static checks and exact file readback only. No physical Sense camera burst, WiFi latency, concurrent microphone/AEC and JPEG memory stress, frame exposure timestamp, model unit trace or 5-pet acoustic trial has passed. Use `code/scripts/bench_head_camera.py` with the actual XIAO to measure camera/status contention. Verify shipped [XIAO Sense OV3660/OV2640 revision](https://wiki.seeedstudio.com/xiao_esp32s3_getting_started/) and mandatory SD J3/USB power isolation physically before electronics assembly.


## November 12 reusable realtime speech protocol and single motion ownership

Further current primary-source comparison:

* [Hugging Face speech-to-speech](https://github.com/huggingface/speech-to-speech) is the open-source low-latency audio agent backing Reachy deployments. It offers an independently running local Silero VAD → STT → LLM → TTS pipeline, OpenAI-compatible Realtime events over WebSocket/WebRTC, and Apple Silicon MLX paths. [Its realtime interface](https://github.com/huggingface/speech-to-speech/blob/main/README.md) measures separate speech recognition, generation and first speech-audio timings. This is a valuable **reference interface and reproducible offline voice baseline**, not a drop-in replacement for our pinned Xiaozhi head, XIAO AEC and fleet lease. No package was installed and its audio latency is not measured on our robot.
* [Reachy Mini's November 3 v1.14.0 SDK release](https://github.com/pollen-robotics/reachy_mini/releases/tag/v1.14.0) explicitly changed concurrent motion requests from silent success to busy errors and guarded wake/sleep/reset over their entire sequences. Our WROOM remains the sole physical safety/motor owner; an agent tool, gaze/emotion event or fleet coordinator cannot turn a concurrent motion denial into a successful pickup. This is a **design pattern comparison**, not imported motion code.
* [Reachy conversation app v1.1.0 and v1.2.0](https://github.com/pollen-robotics/reachy_mini_conversation_app/releases) documents independent local Silero VAD for immediate expressive listening and server VAD for actual turn ownership, plus explicit Wi-Fi dead-socket recovery. Our existing XIAO/ESP-SR and native Xiaozhi transport need real duplicate-VAD and lost-stream trials before claiming equivalent speech interruption.

Next *source-appropriate* test uses **existing** voice bridge and head face-owner modules: inject speech start while spontaneous video, audio generation and body interaction overlap; confirm camera cancellation, single speech lease, no stale TTS output, no unsupervised motor authorization, private-per-pet memory, and actual authenticated VAD reconciliation. Then measure the corresponding delay with physical audio. Do not transplant Reachy's 6DOF head software, install a duplicate speech server, or label protocol similarity as hardware acceptance.

## November 12 upstream release and media-source verification

Rechecked the [official Reachy Mini conversation app releases](https://github.com/pollen-robotics/reachy_mini_conversation_app/releases) through v1.2.0 (released November 4, 2026) and [Pollen's original media architecture article, June 10, 2026](https://huggingface.co/blog/pollen-robotics/reachy-mini-media-stack). This is additional primary-source review, not a new Mac media stack.

* Reachy v1.1.0 specifically places **local Silero VAD** ahead of server turn control: face/antenna movement freezes on detected local speech while the server still decides human turns. Our XIAO/WROOM Stackchan face and authenticated Xiaozhi VAD should analogously stop optional activity promptly; do not import their antennas/head kinematics into our fixed head or grant voice events motor permits.
* Their GStreamer camera pipeline tees one source into WebRTC for remote clients and IPC for local consumers, with an auto-selected receiver. Their article reports **approximately 100 ms** camera-to-display latency on a particular Reachy Wireless and Windows laptop setup, measured externally with an LED and photoresistor. **This is not the XIAO JPEG receipt latency, vision inference time or mechanical response time of our robot.** To compare honestly, our physical tests need an LED/photodiode or equivalent external exposure-to-response timing fixture plus audio VAD-to-speaker-silence timing.
* The reused abstraction is **a single media owner and multiple consumers with explicit priority and freshness**, not necessarily GStreamer or WebRTC. Our current XIAO bridge and Mac `CameraFrameHub` already own snapshots; adding a second 60 fps stream on XIAO would be an unverified RAM, bandwidth and power redesign. Prioritize instrumented JPEG frame receipt, multihead arbitration and genuine human barge-in under one coordinator.
* Their app's local-first memory/profile storage migrations are a reminder to retain our existing per-robot SQLite stores and explicit consent. Do not copy an app-global personality data directory into five independent pets.

Concrete software gap worth testing next: stop an in-flight optional frame capture when local human VAD begins, verify the OLED listening state moves promptly without blocking on Mac VLM, and log sound-activity-to-visible-state latency on a real head. Keep reporting source-level tests separately from acoustic or camera hardware measurements.

## The real secret: its *orchestration*, not a magic LLM or one proactive algorithm

[Reachy Mini source](https://github.com/pollen-robotics/reachy_mini) (Apache 2.0 software) offers a documented app ecosystem, Python SDK, daemon, simulation and managed lifecycle. [Official conversation app](https://github.com/pollen-robotics/reachy_mini_conversation_app) (Apache 2.0) is the most relevant source. The app does **not** rely on the model continuously improvising low-level PWM. Its `src/reachy_mini_conversation_app/moves.py` says explicitly:

* One dedicated ~60 Hz control loop and **one actual output writer** for all expressive joints.
* Queue mutually exclusive *primary* behavior (emotion/dance/pose/breathing); blend only compatible *secondary* gaze and speech offsets. Use a monotonic clock and smooth interpolation.
* Idle **breathing** after a delay, overridden by listening and other activity, makes the robot seem present without constant unsolicited dialogue.
* Local Silero VAD gives a low-latency listening signal; server VAD adjudicates the real spoken turn. A suspected interruption first lowers upcoming audio to **25%**, while a confirmed interruption cancels prior generation. The experimental source says actual already-buffered audio latency and echo still need measurement.
* Camera, emotion clips, memory and head tracking are **narrow tools** with explicit profile permissions, not trusted arbitrary motor-control text.
* Per-profile identity, instructions, voice, greeting and tool permissions matter. An `idle_do_nothing` action is as important as the capability to act.
* Reusable expression data is exposed as [Reachy Mini emotions](https://huggingface.co/datasets/pollen-robotics/reachy-mini-emotions-library) and [dances](https://huggingface.co/datasets/pollen-robotics/reachy-mini-dances-library), but the trajectories target Reachy's 6-DOF head, antennas and body rotation and **cannot be loaded as our SMARS stepper, one OLED and two gripper servo trajectories**. Reuse semantic labels, timing and scheduling; only create a display-specific renderer after real XIAO face interface review.

Official build instructions explicitly distinguish real-time `set_target` (single 50–100 Hz owner) from smooth one-shot `goto_target`. See [motion philosophy](https://github.com/pollen-robotics/reachy_mini/blob/main/skills/motion-philosophy.md), [control loops](https://github.com/pollen-robotics/reachy_mini/blob/main/skills/control-loops.md), [AI integration](https://github.com/pollen-robotics/reachy_mini/blob/main/skills/ai-integration.md), [app lifecycle](https://github.com/pollen-robotics/reachy_mini/blob/main/docs/source/SDK/apps.md). We have an even more important priority: **the WROOM controls stop and motor safety independently of every Mac model**.

**Important nuance:** The official Reachy Mini `camera` tool is normally **on-demand** when the assistant calls it. It is **not evidence that the default official conversation app watches forever and autonomously starts a dialogue upon every new scene**. A community [Judgy Reachy No Phone](https://github.com/yaseminozkut/judgy_reachy_no_phone) uses YOLO phone detection, a bounded intervention cooldown and persona-specific speech/expressions as a real example of a proactive visual *event trigger*. That application is context-specific and not a reason to shame users or covertly monitor their desk.

## The important published research and how we should reuse it

1. **LlamaPIE**, Chen et al., ACL Findings 2025, [paper](https://aclanthology.org/2025.findings-acl.710/): a cheap model answers *when should we offer help*, and a larger model creates the concise *what to say*. **Current integration:** existing `PetController._consider_speech` is a cheap first-pass gate before costly Ollama speech. We strengthened it with source-specific confidence cutoffs and a second check after the slower reply. **Do not claim we imported their trained classifier or that our hand-picked confidence thresholds are statistically calibrated.**
2. **ProAct**, Zhang et al., 2026, [paper](https://arxiv.org/abs/2602.14048) and [project](https://proactrobot.github.io/): fast low-latency behavior and a slower deliberative cognitive system, with high-level intentions inserted asynchronously. **Current integration:** WROOM local safety and tactile IMU loops; Mac asynchronous visual comparison, memory and conversational response; existing XIAO face/speaker. **Gap:** no measured continuously composited nonverbal expression linked to TTS progress. Their full streaming neural motion generator is not a drop-in model for our two MG90S (lift and jaw) and cannot be granted motor authority.
3. **ARISE**, Cheng et al., October 2026, [paper](https://arxiv.org/abs/2610.05964): emphasizes the complete loop from social intent through memory to streaming gesture-and-speech expression. **What to adopt:** integrate the eventual real OLED face states with audio events and preserve one output owner, without making up face motion mechanics.
4. **Sensible Agent**, ACM UIST 2025, [paper](https://doi.org/10.1145/3746059.3747748): proactive agent chooses both **what** help and **how disruptive** the delivery is, including unobtrusive visual rather than spoken output. **What to adopt:** a short nonverbal OLED reaction or staying silent is often better than an unsolicited 15-second monologue. No continuous mobile phone monitoring without consent.
5. **ProactiveBench**, Wang et al., 2025, [paper and code](https://github.com/yellow-binary-tree/ProactiveBench), [abstract](https://huggingface.co/papers/2507.09313): evaluates *timing*, not merely correct words. **What to adopt:** log candidate evidence, voice-active suppression, time-to-first-reaction, interruption false starts and missed genuine events by robot.
6. **RoboOmni**, Wang et al., October 2025, [paper](https://arxiv.org/abs/2510.23763): perceiver, thinker, talker, executor, fuses audio and visual cues to infer context from weak rather than explicit instructions. **What to adopt:** source-tagged WROOM touch/IMU/ToF, XIAO JPEG and live Xiaozhi VAD. Its trained action executor **must not** replace WROOM local motion permits.
7. **Proactive Conversational AI: a comprehensive survey**, Deng et al., ACM TOIS 2025, [paper](https://doi.org/10.1145/3715097): evidence for the divide between context understanding, conversation initiative and actual user benefit. Reuse design principles, **not** an untested end-to-end pretrained policy.
8. **EMOTION**, Apple ML Research, January 2025, [paper](https://machinelearning.apple.com/research/emotion-expressive-motion): models semantic expressive gestures from context. Use a semantic expression dictionary and timing, not the original joint trajectories.

9. **General turn-taking models for human-robot interaction**, Skantze and Irfan, HRI 2025, [paper](https://arxiv.org/abs/2501.08946): TurnGPT and Voice Activity Projection (VAP) can predict whether a pause means turn completion or continuation. A 39-participant evaluation reported fewer unnatural delays and interruptions than a silence-only baseline. **Potential smallest integration:** test end-of-turn prediction as an optional Mac-side advisory signal alongside existing authenticated Xiaozhi VAD; never substitute model inference for urgent device playback abort or for the live speech owner. Do not introduce an extra microphone capture or grant it motor authority.
10. **ProVox**, Grannen et al., 2025, [paper](https://arxiv.org/abs/2506.12248): personalized intent prompts guide proactive assistance during situated physical collaboration. **Potential reuse:** enrich the already existing per-pet, consented initiative scoring with a small user preference and recent refusal context, then evaluate unsolicited speech frequency and perceived helpfulness. Its manipulation planner and quoted user study effects are not evidence of working autonomous grasping on our gripper. Do not add a second agent stack or unsupervised movements.

## One architecture, not competing agents

```text
[XIAO Sense Mic] real VAD -> server live voice floor (already implemented)
[XIAO Sense Camera] authentic JPEG -> Mac frame gate / selective VLM
[WROOM] touch, CAP, MPU6050, 8 VL53L4CD, dock, force/raw buses
                   -> Mac attributed facts in isolated robot SQLite stores
                   -> cheap initiative decision (source confidence / novelty)
                   -> still needed? fleet voice quiet, cooldown and permissions
                   -> slower Ollama / Xiaozhi or approved realtime model
                   -> SECOND speech permission check after reasoning
                   -> existing single Xiaozhi speaker lease (native and legacy)
[WROOM] cliff / touch / dock / motor owner: never driven by this diagram
```

**Already implemented expression reuse:** the local Sense `FaceTask` uses the pinned Stackchan HSM with real touch and speaking events and owns idle OLED moods; the FaceTask explicitly discards Stackchan motor actions. It is not physically qualified, and the robot cannot reproduce Reachy's head/antenna motion with the two already committed MG90S grip/lift servos.

**In source as of this pass:** `code/laptop/src/desk_robot/pet.py` now has `_initiative_evidence` and `_human_active_in_fleet`. It suppresses low-confidence visual guesses, unknown event kinds, stale/replayed duplicate descriptions, all robots' real VAD during a speech candidate, and human turns beginning during the LLM response. Only an actually transmitted remark advances spontaneous speech cooldown. Generated text that is empty or exceeds 280 original characters is **suppressed, not silently truncated** into a misleading spoken fragment. It preserves low-confidence observational memory as uncertain (does not erase it), and existing qualified CAP1188/side range/touch/IMU event categories remain eligible. The active interruption audio floor in `desk_robot_bridge.py` and `desk_robot_native_omni.py` remains the priority owner. New `test_pet.py` cases cover the gate and cross-robot VAD races. **Source committed, not yet compiled or hardware tested**.

## Concrete next source loops, without pretending finished

1. **Safety and output ownership:** keep WROOM hardware stop independent; actual five-robot group TTS must be interrupted by any authenticated human source, not microphone echo. Measure 19/20 immediate stops under 500ms and >=18/20 intent retention on physical heads.
2. **Expression without new hardware:** the selected `code/firmware/head/sense/desk_robot_sense.cc` already runs a **pinned Stackchan-agent `HsmBehavior`** in one 100ms `FaceTask`. It maps real WROOM touch and CAP edges to `kTouched`, real Xiaozhi speaking state to `kSpeakRequest`/`kSpeechFinished`, and idle Stackchan moods to the existing SSD1306 via `display_->SetEmotion`; body faults override to a sad face. **Do not rebuild a parallel face renderer or assume Reachy's 6DOF movements exist.** Verify physical LVGL/I2C timing and extend that same HSM only for genuinely missing listening/thinking/curious states. No jaw, lift or track animation is permitted.
3. **Why not speak?** record exact suppression reason, confidence, human/quiet state and event source without saving raw JPEG/audio. Personalize opportunity thresholds only after real human judgments, not fabricated training data.
4. **Multimodal context:** preserve truthful temporally matched image and microphone evidence across one human turn. Never promote a text-only peer report into a camera witness or inferred identity.
5. **Physical sign-off:** full CAD imported and aligned, correct PCB and power rails, safe charger+fuse/contact isolation, non-guessy last centimeter docking, force-calibrated grab and placement, real speaker flush. All are still required for buy/print/assemble.

## November 12 cognitive-load-aware proactivity review

Primary source: Carsenti et al., *Designing a Robot's Proactivity: Adjusting the Robot's Communication Modality to the Participant's Cognitive Load*, HRI Companion 2026, March 16, DOI https://doi.org/10.1145/3776734.3794456. An 87-person study with ElliQ found participants favored verbal initiative under lower cognitive load and nonverbal initiative under higher load. This is a human-subject design result, **not a validated classifier of our user's concentration and not permission for covert monitoring**.

**Reuse the existing PetController speech gate, authenticated voice floor, camera event coalescing, and single face/speaker ownership.** No extra inference service, robot framework, new recording stream or motion owner is justified. Extend future policy only after inspecting actual preference flags and OLED capabilities:

1. User quiet mode, active VAD, disconnected VAD monitor, hardware fault or an unconsented observation keeps spontaneous audio silent. Local WROOM safety has absolute priority.
2. When an event is worthwhile but the user appears busy from *explicitly consented, low-confidence interaction signals* (for example an active user turn), prefer a tiny permitted nonverbal OLED cue or no action; never infer mental state as fact. No face recognition requirement.
3. When permitted, speech still requires source provenance, freshness, the existing shared speaker lease and a second check after slow language generation. Do not convert a gesture or camera event into new motor permissions.
4. Test that high-priority human speech silences all five pets, that quiet mode cannot be bypassed by nonverbal-to-verbal escalation, and that busy/uncertain contexts cause fewer unsolicited utterances without hiding urgent fault indications. Record false interventions and missed genuine moments per robot.

**Acceptance status:** research reviewed only; no source behavior changed in this note, no repository test or live user study executed, and no claim of cognitive-load sensing or measurable improvement. The immediate implementation target is one narrow regression against the current policy, not a second proactive agent.
