# Live voice framework reuse decision (2026-11-12)

## Scope and existing evidence
This is a research and integration decision for PR #17, not a claim of implemented acoustic full duplex. Read alongside `docs/guides/audio-barge-in.md`, `docs/guides/live-conversation.md`, and `docs/guides/sense-aec-port.md`. The existing architecture already has a Xiaozhi Sense audio path, a Mac generation-aware cancellation controller, an authenticated `/interrupt` route and device TTS stop/flush signaling. The documented missing gate is a real synchronized mic plus post-volume speaker reference for the Sense AFE, followed by measurable human double talk, DMA flush and actual playback acknowledgement. A new voice framework does not solve these device-side problems by itself.

## Smallest integration experiment for the implementation and QA tasks
1. Inspect current Sense `NoAudioCodecSimplexPdm` capture and I2S write paths and `AfeAudioEngine` MR input contract at pinned Xiaozhi revision. Identify exactly where post-gain PCM can be tapped without losing actual accepted playback timing.
2. Add a bounded, Sense-only playback reference adapter behind an opt-in configuration, retaining the existing working baseline. Keep capture and playback generations, frame counts and underflow diagnostics. Never represent a mono mic buffer as two-channel mic/reference samples.
3. Write host-testable reference resampling and interleaving cases: 32 kHz to 16 kHz chunk boundaries (current MAX98357A board contract; 24 kHz was the historical RIO reference, not the active speaker rate), partial writes, underflow, ring wrap, reset during output, obsolete generations and no reference after canceled audio. Do not hold a lock across blocking I2S operations.
4. Build the Sense firmware and inspect ESP-SR device AEC enablement, RAM and 8 MB partition constraints. A successful build is not an acoustic test.
5. Only on actual hardware measure playback echo suppression, double talk preservation, human interruption onset to speaker silence, flush acknowledgement, false self-interruptions and retained user transcripts, with camera, WiFi and motors active. Apply the preexisting 19/20 within 500 ms acceptance gate; report failures explicitly.

## Coordination and licensing
Keep PR #17 canonical; do not create a parallel voice rewrite or close existing work. This note is intended for implementation and independent QA to share via repository docs. No upstream source code was copied. Repository README license labels are preliminary evidence only; verify pinned upstream LICENSE and any bundled DSP model licenses before copying code. Source references and conclusions were researched on November 12, 2026. No firmware compilation, audio tests or physical qualification occurred in this research iteration.

**Concrete upstream fix ported into existing code:** the newer Xiaozhi server `core/providers/tools/server_plugins/plugin_executor.py` moves synchronous plugins off the audio/connection asyncio loop into a dedicated eight-worker `ThreadPoolExecutor`; asynchronous functions remain native coroutines. The original pinned server runs synchronous plugin calls inline, so a slow tool could block other pets' voice progress. Instead of changing all 36 later upstream server commits, `code/laptop/server/install_overlay.py` now uses a single anchored `patch_plugin_executor` transformation on the locked server source to backport the relevant upstream MIT implementation. It preserves the original error response and the conn-parameter contract for tool types 3, 4, and 5. Source commits `aa8ee47`, `7dede64`; `9ef0c15` checks overlay file inclusion and `37560b6` runs a source-level event-loop responsiveness regression against the pinned source fixture when available. **These repository tests have not run in the blocked Actions jobs.** A separate local behavior harness confirmed the concurrency pattern only, not the entire server overlay.

**Camera upstream comparison:** the later `main/boards/common/esp32_camera.cc` changed how a native ESP32 image is synchronously encoded and sent as a multipart upload with Content-Length. Our selected XIAO Sense board is patched at a fixed pin and uses its own authenticated local JPEG receipt path, not that remote camera explain endpoint. Do **not** copy the newer encoder blindly, change the board pin, or claim compatibility without reviewing memory, camera HAL and installed overlay anchors. The latest `main/mcp_server.cc` change adds a restart explanation to device tool descriptions, not a missing physical robot capability. Server post-pin changes include unrelated weather and Home Assistant plugins that should not be imported for parity metrics.

**Still not community-best complete:** no measured local full-duplex AEC/DMA flush, no demonstrated five active XIAO microphones and five cameras with a single authenticated interruption floor, no true physical charging/dock and CAD fit, no calibrated real gripper force, and no reproduced end-to-end source test build. The robot can use modern source patterns, but code existence or upstream version numbers alone never certify a finished robot. Before considering a broad upstream migration, capture the actual compatibility diff, reproduce full host + head + WROOM compilation on the new pin, and run physical AEC, power, and safety regressions. Do not switch production pins automatically.
